# 正式版发布流程与门禁

本流程适用于 GitHub 正式版、固件下载包及在线刷写页面。自 0.7.25 后续发布起执行。

## 必须遵守的发布门禁

**拟发布的确切提交必须在 GitHub Actions 的 `Build and test` 工作流中完成检查，且 `host-tests`（主机测试）和 `firmware`（ESP32 固件构建）全部为 `success`，才能发布正式版并更新在线刷写页面。**

- 本地测试、编译或真机验证通过，不能代替 GitHub 检查通过。
- 排队、运行中、失败、取消、跳过或缺失任一任务，均视为门禁未通过。
- 不得用旧提交的成功记录、另一分支的不同提交或仅一个任务成功作为放行依据。
- 修复后必须推送新提交，并等待该提交的全部检查通过；不得先发布再补修测试。
- 去掉 `-dev`、修改版本号或其他发布内容后，必须重新确认最终提交的检查结果。

## 发布顺序

1. **准备正式版提交。** 完成代码、版本号、文档与验证记录；执行适用的本地回归、构建和真机检查。将最终提交推送到 GitHub。
2. **等待 GitHub 门禁通过。** 核对工作流的 `headSha` 等于拟发布提交 SHA，工作流已完成且成功，`host-tests` 和 `firmware` 均成功。记录提交 SHA、运行链接与结果。
3. **创建版本标签。** 标签必须指向上述已通过检查的确切提交，不使用可能继续变化的分支头替代。标签推送会触发当前仓库的另一轮检查，也必须等待该轮全部通过后再发布正式 Release。
4. **发布正式版与下载包。** 产物必须来自该提交，固件内版本号、文件名、发布说明保持一致；生成并核对 SHA256。发布为非草稿、非预发布版，确认 Release 附件完整可下载。不得随意移动已发布标签或替换同名固件。
5. **最后更新在线刷写页面。** 先上传到独立版本目录并校验，再更新默认 manifest、ZIP 下载入口与版本说明。保留上一正式版及回退文件，不先切换清单再上传固件。
6. **验证公开入口。** 用浏览器确认页面显示正式版号、版本查询和下载链接正确；从公网下载固件与 ZIP，对比本地校验值。若本次包含刷机，读回设备版本、联网和音频状态，分别记录。

## GitHub 检查方法

在仓库目录执行，使用本次真实运行 ID 替换 `RUN_ID`：

```sh
git rev-parse HEAD
gh run list --workflow 'Build and test' --commit "$(git rev-parse HEAD)" \
  --json databaseId,headSha,headBranch,event,status,conclusion,url
gh run watch RUN_ID --exit-status
gh run view RUN_ID --json headSha,status,conclusion,jobs,url
```

必须检查 JSON 中两个任务的名称和结果，不能只凭“运行已结束”或没有收到失败邮件判断成功。标签运行也按同样方法核对 SHA 与任务结果。

当前工作流定义见 [build.yml](../.github/workflows/build.yml)。工作流任务变更时，应同步维护本文的门禁名称。

## 失败处理与发布记录

门禁未通过时，保持当前公开正式版和在线刷写默认版本不变。查看失败日志、修复、推送并等待新运行全部通过。不要通过跳过测试、删除失败记录或仅重跑旧错误提交来掩盖问题。

每次发布记录至少包含：版本、提交 SHA、分支和标签的 GitHub 检查链接及结果、产物校验值、公开页面验证、真机验证范围和回退版本。尚未验证的项目必须明确列出。

本流程目前是发布操作规范；现有工作流负责测试和构建，并未自动阻止手工创建 Release 或部署网页。执行发布的人或代理必须主动核对并遵守此门禁。
