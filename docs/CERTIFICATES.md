# 设备证书与中继信任

## 普通用户：申请本机设备证书

设备首次启动会在本机生成 Ed25519 密钥。私钥保存在设备 NVS，不随证书申请上传。申请必须在需要使用的那一台设备的网页后台发起。

1. 联网后，在“设备证书”填写自己的呼号。
2. 填写**已有 FMO 设备或账号的 UID**，供管理员核实身份。它不是新 M5 的设备 UID，不要直接复制为新设备编号。
3. 选择 M5 / AI Passport / 其他 ESP32，上传实际设备照片。
4. 提交审核。浏览器会压缩照片并经 HTTPS 提交；设备提交带持钥签名的申请。
5. 管理员审核照片和现有 FMO UID 后签发。新设备 UID 由签发系统分配。
6. M5 在空闲且联网时约每 60 秒检查一次结果。验证根信任、公钥、呼号、有效期和签名链后安装，保留上一次证书作为回退；随后尝试接入中继。

提交申请不会立即获得证书。管理员入口是 [BH1JSS 后台](https://app.bh1jss.net/m5-certificates/)，需要管理员登录；普通用户不需要管理账号。

**本仓库只发布终端侧代码。** 托管申请服务由维护者运营，服务器审核后台和签发私钥不在此仓库。第三方自行部署签发服务，需要自行实现匹配接口、审核和编号管理；复制固件不会获得签发权限。

## 已有证书：手动导入

在本机网页导出申请，将其交给签发者，再把收到的 JSON 证书包导入这台设备。包包含 `rootCert`、`intermediateCert`、`userCert`；具体语义与签名按 FMO 证书格式校验。

导入页面需要明确确认信任签发机构。证书必须绑定本机公钥和呼号；篡改、越权编号、签名错误、错绑公钥均应被拒绝。**不要导入 CA 私钥，也不要把一台 M5 的证书复制给另一台。**

BI4TES / Passport 根也不能单独代替用户证书。使用另一套 CA，需要对方签发匹配本机公钥的完整证书链，并且目标中继信任该链。当前自动领取流程固定使用 BH1JSS 的根公钥和申请接口；本版没有集成 BI4TES 自动申请服务。

## 中继管理员：只添加根信任

你不需要替所有用户逐台导入证书。

1. 下载 [bh1jss-m5-root.json](../public-certificates/bh1jss-m5-root.json)，或在设备网页的服务器管理员入口下载。
2. 与维护者核对证书来源及文件校验值；可运行 `shasum -a 256 bh1jss-m5-root.json`（Linux 可用 `sha256sum`）。本版本校验值见 [ROOT_SHA256SUMS](../public-certificates/ROOT_SHA256SUMS)。
3. 将文件加入**实际运行的 SAS 服务**使用的 `--roots-dir` 目录，例如 `~/.sas/roots/`；服务账户的 HOME 可能和登录用户不同。
4. 保留已有官方 / 其他受信任根，按自己的维护流程重新加载或重启 SAS。
5. 用一台已获批的 M5 登录验证，并检查 SAS / MQTT 授权日志。

`bh1jss-m5-issuer.json` 是公开的中间 CA 信息，供核对签发链；服务器信任入口应使用根文件。不能把一个自建中间证书放进去就宣称获得了官方授权。

```text
BH1JSS M5 Root CA（独立根）
  └─ BH1JSS 的中间 CA（签发设备证书）
       └─ 某台 M5 的用户证书（绑定设备公钥与 UID）
```

服务器可同时信任多套根，但是否接纳由每台服务器管理员决定。信任这套证书链只解决身份验证，不自动保证服务器发现、集群互通、频道权限或所有音频格式兼容。

## 传输与存储边界

当前实时 MQTT 和设备轮询接口使用明文 TCP / HTTP；申请和证书有签名校验，**签名不等于传输保密**。照片在浏览器侧通过 HTTPS 上传。固件当前未启用 NVS 加密、Secure Boot 或 Flash Encryption；具有设备物理读出能力的人可能取得持久化的密钥。不要将设备网页映射到公网，整机备份应妥善保管。

公开根证书不是秘密，也不能用于生成用户签名；CA 私钥才具有签发能力，必须由签发方保管。证书信任、人工审核和联网语音各有独立边界。
